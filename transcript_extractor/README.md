# Семантическое дополнение словаря аббревиатур

Этот этап использует языковую модель для извлечения связи «сокращение — полное
название». Он предназначен для оставшихся кандидатов после Schwartz–Hearst
и предыдущего извлекателя. Буквенное соответствие не является обязательным:
модель может распознать слитное слово, перевод или явно указанное локальное название.

Алгоритм: поиск контекстов → извлечение LLM → проверка цитаты → повторное
извлечение другим запросом → добавление совпавших пар в словарь.

## Что уже сделано и что ещё нужно запустить

В архиве находятся:

- `resolve_abbreviations_llm.py` — автономный скрипт, Python 3.10+, только стандартная библиотека;
- `dictionary_input.csv` — входной словарь с 359 подтверждёнными записями и 4 125 кандидатами;
- `llm_tasks.jsonl` — подготовленные задания с текстами и ссылками на источники;
- `candidate_audit.csv` — частоты, отобранные контексты и подсказки о SQL-ключевых словах;
- `preparation_summary.json` — результаты подготовки;
- `test_llm_stage.py` и `validation_report.json` — проверки кода и происхождения контекстов.

Подготовка на ваших файлах выполнена. **Реальная LLM в среде создания этого
архива не запускалась: сервера Ollama/API здесь нет. Новых подтверждений этим
этапом пока не добавлено.** Число новых пар покажет `llm_summary.json` после
запуска у вас. Результаты тестового API не подставлены в рабочий словарь.

## Быстрый запуск в Windows через Ollama

Распакуйте архив и откройте PowerShell в каталоге `abbreviation_llm_stage`.
Ollama должна быть установлена и запущена. Если модель ещё не загружена:

```powershell
ollama pull qwen3:8b
```

Полный проход по подготовленной очереди:

```powershell
python .\resolve_abbreviations_llm.py run `
  --dictionary .\dictionary_input.csv `
  --tasks .\llm_tasks.jsonl `
  --provider ollama `
  --model qwen3:8b `
  --output-dir .\llm_results
```

`qwen3:8b` здесь — стартовая конфигурация, а не модель, качество которой
проверено на вашей разметке. Можно указать другой установленный тег модели.
Если Ollama не отвечает на `127.0.0.1:11434`, запустите приложение Ollama
или `ollama serve` в другом терминале.

Для небольшого первого прогона добавьте `--limit 100`. Затем повторите ту же
команду без ограничения: завершённые задания будут прочитаны из сохранённого
состояния, оставшиеся продолжатся. `--limit` ограничивает новые задания за
один запуск, а не номер последней строки очереди.

`Ctrl+C` останавливает процесс с сохранением завершённых заданий. Не удаляйте
`llm_results/state.sqlite3`. Проверка тоже кешируется, поэтому после остановки
между извлечением и проверкой первый ответ не нужно получать заново.

По умолчанию используется контекст Ollama `16384` и до 6 фрагментов на кандидата.
Если модель не помещается в видеопамять, уменьшите контекст вместе с размером
подготавливаемых заданий, либо используйте меньшую модель. Реальное потребление
памяти и скорость этого прогона на вашем ПК не измерялись.

## Запуск через API на виртуальной машине

Поддерживается API с контрактом `/v1/chat/completions`, например ваш сервер
модели. Конкретный endpoint и имя модели зависят от того, как она развёрнута.
Никакой адрес Cloud.ru в код не зашит.

PowerShell, если API требует ключ:

```powershell
$env:LLM_API_KEY = "ВАШ_КЛЮЧ"
python .\resolve_abbreviations_llm.py run `
  --dictionary .\dictionary_input.csv `
  --tasks .\llm_tasks.jsonl `
  --provider compatible `
  --base-url "http://АДРЕС_ВМ:8000/v1" `
  --model "ИМЯ_МОДЕЛИ_НА_СЕРВЕРЕ" `
  --output-dir .\llm_results_cloud
```

В `--base-url` для compatible указывается базовый адрес до `/v1` включительно,
без `/chat/completions`. Для Ollama — адрес до порта, без `/api/chat`.
Используйте HTTPS, если он предусмотрен вашим сервером. Ключ берётся из
переменной окружения, по умолчанию `LLM_API_KEY`, и не записывается в результаты.

По умолчанию запрашивается JSON Schema. Если сервер поддерживает только
JSON mode, добавьте `--response-format json`. Локальная валидация и проверки
доказательств при этом сохраняются. При HTTP-ошибке скрипт сохраняет уже
выполненную работу и останавливается, а не делает тысячи неудачных запросов.

Linux использует те же аргументы. Символ переноса строки — `\` вместо
PowerShell-символа `` ` ``. Переменная ключа задаётся как
`export LLM_API_KEY='ВАШ_КЛЮЧ'`.

## Как принимается решение

1. **Подготовка.** Алгоритм Aho–Corasick ищет все кандидаты словаря за один
   проход по каждому тексту. Это только поиск упоминаний. Он не подтверждает
   расшифровки и не требует заглавных букв или совпадения инициалов.
2. **Отбор контекстов.** Окна ранжируются по признакам определения. Жадный
   отбор уменьшает число похожих окон и добавляет разнообразие документов.
   `retrieval_score` — приоритет текста для чтения, а не вероятность правильной пары.
3. **Извлечение.** Модель получает сокращение и несколько контекстов. Она
   возвращает полное название, тип связи и дословную цитату либо пустой список.
4. **Проверка источника.** Код проверяет существование `context_id`, точное
   присутствие цитаты, наличие сокращения и полного названия в одной цитате.
   Допускается только нормализация пробелов. Перефразирование и дописанные
   слова не принимаются.
5. **Повторное извлечение.** Второй запрос получает один исходный контекст.
   Предложенная первой моделью расшифровка в этот запрос не передаётся.
   Для подтверждения должны совпасть извлечённое название и тип связи.
6. **Обновление.** Согласованные пары добавляются в `expansions_json`,
   сохраняются цитаты и ссылки, устанавливается `status=confirmed`.
   Исходные подтверждённые записи не изменяются.

Разрешённые типы связи:

| Тип | Значение |
|---|---|
| `expansion` | Полное название сокращения, явно связанное с ним в тексте |
| `translated_expansion` | Явно приведённое автором полное название на другом языке |
| `description` | Описание назначения, функции или свойств; автоматически не подтверждается |

Например, `PIN — персональный идентификационный номер` может пройти без
сопоставления латинских и русских букв. `JSON — формат обмена данными`
не является полной расшифровкой и должен остаться описанием.

Смысловая часть выполняется LLM. Регулярные выражения используются при отборе
контекстов и проверке границ упоминания, а не для принятия смыслового решения.

Один и тот же модельный тег по умолчанию используется с двумя разными запросами.
Это **не независимые эксперты**, их ошибки могут совпадать. Для отдельной
модели проверки можно указать `--verifier-model ДРУГАЯ_МОДЕЛЬ`, если она доступна
на том же API. Совпадение двух ответов не является гарантией точности.

## Что получится после запуска

| Файл | Содержимое |
|---|---|
| `dictionary_llm.csv` | Полный обновлённый словарь |
| `new_pairs_llm.csv` | Новые подтверждённые пары и доказательства |
| `candidate_audit_llm.csv` | Решение по каждому кандидату, тип и краткая причина |
| `review_llm.csv` | Отклонённые предложения: нет цитаты, расхождение ответов, описание вместо расшифровки и т. п. |
| `llm_summary.json` | Новые подтверждения, остаток кандидатов, число запросов, причина остановки |
| `state.sqlite3` | Ответы и результаты для продолжения после остановки |
| `run_config.json` | Совместимость настроек и задания для безопасного продолжения |

`confirmation_method` новых подтверждений — `llm_grounded_double_extraction_v1`.
Существующие поля словаря сохраняются. По умолчанию хранится до 3 ссылок на
каждую новую расшифровку. Одинаковая цитата в одном документе не наращивает
число доказательств при повторении в перекрывающихся чанках.

Модель может предположить, что кандидат — SQL-ключевое слово, идентификатор,
обычное слово или название продукта. Такая классификация записывается в отчёт,
**но сама по себе не меняет исходный `status=candidate` и не увеличивает число
подтверждённых пар**.

Для NER-контекста ссылка относится ко всей группе `context_chunk_ids`:
определение может находиться в соседнем чанке. `anchor_page` — страница якоря,
а не доказанная страница определения. Для прямого JSONL источником является
конкретный чанк и его страница. Цитаты имеют исходные символьные смещения,
номер записи и SHA-256 текста контекста.

## Подготовка заданий из другой или обновлённой выгрузки

Не нужно запускать `prepare` повторно для приложенной очереди. Для своих новых
файлов используйте:

```powershell
python .\resolve_abbreviations_llm.py prepare `
  --dictionary .\glasary\resolved\dictionary_resolved.csv `
  --abbreviations .\glasary\abbreviations.csv `
  --chunks .\glasary\chunks.csv `
  --documents .\glasary\documents.csv `
  --tasks .\prepared\llm_tasks.jsonl
```

При наличии полного актуального текстового корпуса добавьте
`--chunks-jsonl .\corpus_processed\chunks.jsonl`. Поддерживаются поля `text`
или `page_content`, `chunk_id` и метаданные документа, в том числе вложенный
`metadata`. JSONL можно использовать отдельно от NER CSV.

`chunks.csv` нужен для метаданных и проверки источников, он не содержит текстов.
Приложенный ранее `chunks(1).jsonl` относится к другой выгрузке и здесь не
использовался: его идентификаторы не совпадают с текущими NER-данными.

Для большего охвата можно увеличить `--max-contexts`, `--max-per-document`
и `--max-context-chars`. Это увеличивает объём запросов и требования к
контекстному окну модели. Внутри каждого исходного NER-контекста выбираются
до трёх окон с наибольшим приоритетом, а не только первое упоминание.

Если меняются модель, параметры генерации, промпты или файл заданий, используйте
другой `--output-dir`: скрипт защищает результаты прошлого запуска от перезаписи
несовместимым проходом. Полученный `dictionary_llm.csv` можно использовать как
вход следующего этапа; подтверждённые записи будут пропущены.

## Ограничения и проверка качества

- Если расшифровки нет в доступных текстах, модель не имеет права подтверждать
  общеизвестное название из своей памяти. Для таких случаев нужен отдельный
  источник определений и раздельные ссылки на определение и употребление.
- Даже при совпадении ответов модель может ошибиться в связи между словами.
  Проверьте первые новые пары вручную; измерить точность можно только на разметке.
- OCR-контексты не дают автоматических подтверждений и попадают на проверку.
- Подготовка ограничивает число контекстов. `no_definition_in_selected_contexts`
  означает отсутствие принятого определения в выбранных фрагментах, а не во
  всём исходном корпусе.
- 2 149 из 4 125 оставшихся кандидатов встречаются один раз. В очереди есть
  команды, фрагменты формул и названия продуктов. Все 4 125 не обязаны иметь
  расшифровки.

Проверки инфраструктуры:

```powershell
python -m unittest -v test_llm_stage
```

Тестовый HTTP-сервер имитирует оба API. Эти тесты проверяют формат запросов,
цитаты, отклонение выдуманных фрагментов, согласие двух проходов, сохранение
исходного словаря и продолжение работы. Они не оценивают качество реальной LLM.

## Источники подхода и API

Скрипт — собственная реализация извлечения с проверкой доказательств, а не
воспроизведение метрик или кода конкретной статьи. Использование LLM для
поиска расшифровок в окружающем тексте исследуется, например, в работе:

- Ali et al., *Automated Extraction of Acronym-Expansion Pairs from Scientific Papers*, 2024: https://arxiv.org/abs/2412.01093
- Ollama Chat API: https://docs.ollama.com/api/chat
- Ollama Structured Outputs: https://docs.ollama.com/capabilities/structured-outputs
- Совместимый API Ollama: https://docs.ollama.com/api/openai-compatibility
- Тег стартовой модели: https://ollama.com/library/qwen3:8b
