# Проверка chunks(4).jsonl и готового решения

Проверен именно полный файл `chunks(4).jsonl` размером 111 519 540 байт.
Отдельный OCR-файл и старые версии чанков не использовались для построения базы.
Исходные данные не изменялись. Дата проверки: 23 сентября 2026 года.

Структурно корпус подходит для построения начальной базы знаний. Отметки качества
и повторяющиеся тексты требуют оценки влияния на поиск. Эта проверка не подтверждает
правильность каждого извлечённого текста относительно каждого исходного PDF.

## Целостность

Проверены все строки JSONL. Не обнаружено ошибок JSON, пустого текста, повторяющихся
`chunk_id`, недопустимых номеров страниц, несоответствий SHA-256 текста,
ссылок на отсутствующих соседей, переходов по соседним ID в другой документ,
нарушения взаимности ссылок или разрывов/циклов цепочек документов.
Номера `chunk_index` уникальны внутри каждого документа.

Найден один пропуск последовательного номера:

- Документ: `linter/bb4c3e6adf63_sql.pdf`.
- Страница 403, `chunk_index=605`, ID `2cc797dbc8892519c36661af9ea94786`.
- Следующий чанк: страница 404, `chunk_index=607`, ID `9598c6b8914d811ef304a0b11a15f3f0`.

Причина отсутствия номера 606 из одного JSONL не устанавливается. Ссылки между
605 и 607 взаимные, вся цепочка достижима. Код использует `prev_chunk_id` и
`next_chunk_id`, поэтому эта особенность не препятствует расширению контекста.
При желании стоит проверить соответствующие страницы исходного PDF.

## Политика обработки

- Повторное разбиение не выполняется. Таблицы остаются в исходном Markdown.
- По умолчанию включены все 39 082 записи. OCR не удаляется автоматически.
- `needs_review` сохраняется для диагностики; это не автоматическое исключение.
- Для повторного текста внутри одного PDF поисковая выдача сохраняет одну запись
  и дополнительные найденные ссылки. Хранилище содержит все записи и ссылки соседства.
- Источники разных документов остаются отдельными, даже при одинаковом тексте.
- При неизвестном разделе контекст опирается на документ и соседство страниц.

## Длины настоящего токенизатора Qwen

Все 39 082 индексируемых текста, включая добавленные имя PDF, папку и раздел,
проверены токенизатором `Qwen/Qwen3-Embedding-0.6B`.

- Минимальный вход после добавления метаданных: 25 токенов.
- Максимальный: 1 680 токенов.
- Входов длиннее настроенного лимита 2 048: 0.

Следовательно, этот корпус в текущем формате помещается в заданный лимит.
При построении индекса длина проверяется повторно. Увеличение метаданных или
смена модели могут изменить результат; скрытое обрезание в коде запрещено.

## Проверки поиска

1. Восемь автоматических тестов прошли. Использован настоящий FAISS для проверки
   записи/чтения, поиска, фильтрации, RRF, источников, OCR-фильтров, соседства,
   бюджета контекста и повреждённых файлов. В этих тестах векторы небольшие,
   детерминированные; качество Qwen они не измеряют.
2. BM25 создан по всем 39 082 чанкам. Обработаны все пять заполненных вопросов
   из `evaluation__train.xlsx`. Форматированный диапазон Excel больше, но остальных
   непустых вопросов в нём нет. Выдача сохранена в `checks/bm25_full_corpus_eval.jsonl`.
3. Проведена отдельная проверка настоящей Qwen3-Embedding-0.6B на CPU: загрузка
   модели, векторы восьми реальных чанков, сохранение FAISS, повторная загрузка
   базы с моделью и гибридный поиск через LangChain `.invoke()`.
   Размерность — 1024. Ревизия модели: `97b0c614be4d77ee51c0cef4e5f07c00f9eb65b3`.
   В небольшой проверочной выборке запрос о CTS вернул первым таблицу с
   расшифровкой `Corporate Transport Server` из `express/f4b30492b8c2_outlook-add-in.pdf`,
   PDF-страница 5. Этот релевантный пример был намеренно включён в выборку вместе
   с семью другими чанками. Это проверка работы компонентов, не метрика полного корпуса.

Использованы Python 3.12, `langchain-core 1.6.4`, `langchain-community 0.4.2`,
`faiss-cpu 1.15.1`, `rank-bm25 0.2.2`, `nltk 3.10.3`.
Для реальной модели использованы `torch 2.8.0+cpu`, `sentence-transformers 5.7.0`,
`transformers 4.57.6`. Проверка CUDA и интеграция с запущенной Ollama здесь
не выполнялись.

## Что уже видно из BM25

В запросе о первом обращении DKP в начале выдачи находится руководство Deckhouse,
PDF-страницы 9–10. В запросе о настройке SNMP находятся фрагменты руководства Kaspersky.
Это проверка источников выдачи; наличие всех обязательных фактов ещё надо оценить.

Есть характерные ошибки ранжирования. Для вопроса о расшифровке CTS вверху
оказались фрагменты с частыми упоминаниями CTS и eXpress; сама расшифровка есть
в корпусе. В вопросе одновременно о ЛИНТЕР и Tarantool первые результаты BM25
пришли из PostgreSQL из-за общего термина WAL. Поэтому одного BM25 недостаточно,
а улучшение от гибрида нужно измерить после полной индексации. Для вопросов,
охватывающих несколько продуктов, следующим улучшением может быть разбиение
вопроса на отдельные поисковые запросы и объединение их источников.

## Что остаётся выполнить на рабочей машине

Полный векторный индекс на 39 082 чанка здесь не строился. В архив включены код,
инструкции и отчёты проверок. Полный FAISS создаётся командой `kb.py build` на
рабочей машине; входной JSONL и веса модели в архив не дублируются.

После построения сравни BM25, FAISS и hybrid на одинаковых вопросах. Для настоящих
Hit@k, Recall@k и MRR@k нужна разметка релевантных `chunk_id`: текущий Excel содержит
ответы и факты, но не такую разметку. В `evaluate.py` ответы используются только
как справочные поля выгрузки, без подмешивания в поисковый запрос.
